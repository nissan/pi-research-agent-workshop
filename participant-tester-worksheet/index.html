Tester Worksheet: Specialist Research Agent Workshop

Follow this sheet exactly to verify the public Docker image supports the learning exercises: baseline agent using either Pi login with an OpenAI Codex subscription or an OpenRouter key with about $5 credit, specialization, harness comparison, solution/fallback paths, and later model swap.

Goal for the tester: confirm a participant can pull the published image, start it, enter the running container when needed, run each learning exercise, and record whether the expected outputs appear.
45-minute workshop note: the primary participant experience is now the browser-level Chat Lab. Verify that the room can open /chat, click Run all three modes, and review the finished conversations before anyone is pushed into file inspection. Treat output files and traces as secondary, post-workshop exploration.

Troubleshooting FAQ added

The workshop collateral now includes TROUBLESHOOTING-FAQ.md. Use it for auth/provider issues like Hugging Face 401/403, OpenRouter rate limits/daily limits/402 insufficient credits, wrong button/lane selection, missing env vars, port conflicts, and fallback recovery.

Tester rule: every live run should show a visible Running... indicator. If OpenRouter returns a 429 rate-limit, daily-limit, or 402 insufficient-credit response, the current image should show a clear limit panel and copy fallback outputs automatically. For any other live auth/model access, network retrieval, or model/tool stall lasting more than 3–5 minutes, record the exact symptom, click Use fallback sample outputs, and continue validating the learning flow. If Docker CLI or the browser endpoint becomes unresponsive, restart Docker Desktop/Engine once, rerun the same container command, and resume from fallback/solution.

Important setup note: use docker exec, not SSH into the container

The image does not need an SSH daemon, and adding SSH would create extra setup and security surface. For this test, treat docker exec -it ... bash as the “SSH into the running container” step. If your container is running on a remote VM, SSH to the VM first, then run the same docker exec commands on that host.

# Local machine
ssh user@remote-host   # only if the Docker host is remote

docker exec -it pi-research-agent-workshop bash

0. Presenter framing to listen for

As you test, the presenter script should be making the “why” explicit, not just asking participants to click buttons.

  • Generic baseline: “First we see what a general agent does with minimal structure.”
  • Chat-first framing: “For the workshop we review the finished chats in the browser first. The files and traces are there for deeper inspection later.”
  • Specialization: “Now we add task-specific tools, evidence sources, and domain knowledge.”
  • Harness: “Prompts ask; harnesses enforce. The harness creates boundaries, validates outputs, and leaves traces.”
  • Model swap: “The specialist architecture should survive swapping the underlying model — Pi/OpenAI Codex to OpenRouter, or OpenRouter model A to model B — but we must record model provenance and review quality.”
  • Fallback/solution: “If auth or network access fails, learning continues with sample outputs and a solution folder.”

4. Credential/auth path

Use one of two participant credential paths. Participants who already have an OpenAI Codex subscription should use Pi /login inside the container. Participants without that subscription should use an OpenRouter key and add about $5 credit before class. Do not write secrets into files.

OpenRouter workshop warning: OpenRouter :free models are request-limited. Official docs describe a 20 requests/minute cap plus daily request caps that improve after buying credits; accounts with low/negative balance can also see 402 insufficient credits. For a group workshop, recommend participants add about $5 credit before class if live calls need to keep working.

Option A — Pi login with OpenAI Codex subscription

docker exec -it pi-research-agent-workshop bash
cd /workshop/starter
pi
# Inside Pi, run:
/login

Option B — OpenRouter API key with about $5 credit

Stop and restart the container with the OpenRouter key as an environment variable. Do not mount pi_workshop_home for this lane.

docker rm -f pi-research-agent-workshop
export OPENROUTER_API_KEY="sk-or-your-key-here"

docker run --rm -it \
  --name pi-research-agent-workshop \
  -p 8787:8787 \
  -e OPENROUTER_API_KEY="$OPENROUTER_API_KEY" \
  -v pi_workshop_outputs:/workshop/starter/outputs \
  nissan/pi-research-agent-workshop:latest

Do not reuse pi_workshop_home for the OpenRouter lane after previous Claude/Pi login tests. If stale auth may exist, reset it before starting:

docker rm -f pi-research-agent-workshop 2>/dev/null || true
docker volume rm pi_workshop_home 2>/dev/null || true

Expected

  • Either Pi can run authenticated prompts, OpenRouter can run with OPENROUTER_API_KEY, or the tester records auth as blocked and uses fallback outputs in step 8.
  • No token is saved in markdown or committed files.
Presenter note: say clearly that the Docker image contains no baked credentials. That is intentional: shippable agents should separate software from secrets.

5. Exercise A — generic baseline

In the browser, click Run generic agent for the Pi/OpenAI Codex lane, or Run generic agent with OpenRouter for the OpenRouter lane. If you prefer CLI, run:

docker exec -it pi-research-agent-workshop bash
cd /workshop/starter
# Pi/OpenAI Codex lane:
pi -p "Read the project instructions and generate the research brief requested in inputs/generic-brief-request.md. Use sources/source-notes.md. Write the result to outputs/research-brief-generic.md."

# OpenRouter lane:
pi -p \
  --provider openrouter \
  --model z-ai/glm-4.5-air:free \
  "Read AGENTS.md and inputs/generic-brief-request.md. Use sources/source-notes.md. Write outputs/research-brief-generic.md. Include provider/model used, source notes used, limitations, and open questions."

Inspect output:

cat outputs/research-brief-generic.md

Expected

  • outputs/research-brief-generic.md exists.
  • The brief is plausible but relatively generic.
  • The UI Outputs list links to the generated artifact.
Presenter note: ask participants what is missing from the generic output: evidence quality, domain specificity, repeatability, and validation.

6. Exercise B — specialize with tools and sources

In the browser, click Run specialized arXiv agent for the Pi/OpenAI Codex lane, or Run specialized arXiv agent with OpenRouter for the OpenRouter lane. CLI equivalent:

docker exec -it pi-research-agent-workshop bash
cd /workshop/starter
pi -p "Use the arxiv-literature-scan and pdf-evidence-reader skills. Identify a research keyword, search arXiv, rank results, read the best PDF if available, then write outputs/arxiv-ranked-results.json, outputs/pdf-evidence-notes.md, outputs/research-brief-specialized.md and outputs/delta-notes.md."

Inspect:

ls -la outputs
cat outputs/research-brief-specialized.md
cat outputs/delta-notes.md

Expected

  • outputs/research-brief-specialized.md exists.
  • outputs/delta-notes.md explains what improved versus the baseline.
  • Specialized output uses evidence/sources more explicitly than the generic baseline.
  • If live network/model fails or stalls for 3–5 minutes, the tester records the failure and continues with fallback in step 8.
Presenter note: highlight that specialization is not “a better prompt” alone. It is prompt + skills + tools + sources + expected outputs.
