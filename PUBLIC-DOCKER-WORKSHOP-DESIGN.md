# Public Docker Workshop Design — Research Agent Builder

## Positioning

Yes: the right participant experience is a public, pull-and-run Docker image, not a VPS shell. The VPS sandbox remains instructor rehearsal/fallback only.

The workshop image should contain everything needed to learn the pattern offline except provider credentials:

- starter workshop files;
- Pi installed and pinned;
- project-local Pi extensions/tools;
- skills and prompt templates;
- an HTMX web UI for invoking the agent and watching tool calls;
- sample inputs and a final completed solution folder participants can inspect when stuck.

## Participant promise

By the end, each participant has a local container where they can:

1. run a generic research brief agent;
2. add one specialization layer;
3. let the agent search arXiv from a research keyword;
4. read/summarize matching PDFs;
5. inspect tool calls and intermediate evidence in a small browser UI;
6. compare their work with a complete solution;
7. map the specialist to a Reddi Agent Protocol-style listing.

## Docker delivery model

Public image name candidate:

```bash
docker pull nissan/pi-research-agent-workshop:latest
```

Run command:

```bash
docker run --rm -it \
  -p 8787:8787 \
  -v pi_workshop_home:/home/piuser/.pi \
  -v pi_workshop_outputs:/workshop/outputs \
  nissan/pi-research-agent-workshop:latest
```

Container starts a lightweight workshop launcher that prints:

```text
Open http://localhost:8787
Then choose:
1. Open Pi CLI
2. Open workshop web UI
3. View solution folder
4. Reset outputs
```

For simplicity, the first image can run a single Python/FastAPI or Node server on `8787` and keep Pi CLI available through `docker exec -it <container> bash` or an optional local tty page. If a browser terminal is included, it must bind only to localhost by default.

## Credential posture

Do **not** bake credentials into the public image.

Supported options:

1. Participant uses `/login` inside Pi with their own provider account.
2. Instructor provides a short-lived workshop API key via environment variable:

```bash
docker run --rm -it -p 8787:8787 \
  -e OPENAI_API_KEY="$WORKSHOP_OPENAI_API_KEY" \
  nissan/pi-research-agent-workshop:latest
```

3. Fallback mode uses bundled sample outputs if auth fails.

The image can include scripts that configure Pi from env vars at container start, but secrets must live only in container runtime state/volume, never in the image layers or repo.

## Agent/tooling architecture

### Pi extension: `workshop-tools.ts`

Use a project-local Pi extension in `.pi/extensions/` so Pi discovers it automatically. The extension registers safe workshop tools:

- `arxiv_search(query, max_results, year_from?)`
- `rank_arxiv_results(results, criteria)`
- `read_pdf(url_or_path, max_pages?)`
- `write_workshop_trace(event)` or direct event hook for tool-call logging

Why extension tools instead of shell-only scripts:

- they are visible as proper agent tools;
- tool calls can be logged and rendered in the UI;
- parameters can be constrained;
- network/PDF limits can be enforced.

The Python scripts can remain the implementation layer behind the TypeScript extension.

### arXiv search tool

Minimum behavior:

- accepts a keyword/topic generated by the agent;
- queries arXiv API;
- returns title, authors, abstract, published date, categories, PDF URL, and arXiv ID;
- writes raw result JSON to `outputs/arxiv-results.json`;
- rate limits and caps results to avoid abuse.

### PDF reader tool

Minimum behavior:

- downloads a selected PDF to `outputs/pdfs/`;
- extracts first N pages or sections;
- returns excerpted text plus metadata;
- writes `outputs/pdf-evidence-notes.md`;
- enforces max file size, page count, timeout, and domain allowlist (`arxiv.org`).

Use `pypdf` or `pymupdf` if available. Prefer `pypdf` first for a simpler dependency footprint.

### Ranking tool

Ranking criteria should be explicit and teachable:

- topic match;
- recency;
- method relevance;
- evidence usefulness;
- actionability for the buyer;
- source quality/confidence.

The agent should rank papers and explain why it chose the top 3.

## HTMX front end

Purpose: make the agent legible outside the CLI.

Pages:

1. **Home** — workshop steps, auth status, run buttons.
2. **Run Generic Agent** — sends the baseline prompt to Pi RPC or a wrapper command.
3. **Add Specialization** — lets participants choose prompt/skill/tool/custom-info path.
4. **Tool Trace** — live-ish event stream showing arXiv search, PDF read, file writes, and generated artifacts.
5. **Compare Outputs** — side-by-side generic vs specialized brief + delta notes.
6. **Peek at Solution** — browsable final folder with spoiler warning.

Implementation options:

- **Recommended:** web app talks to Pi in RPC mode (`pi --mode rpc`) and renders JSONL events.
- **Simpler first cut:** web app shells out to `pi -p` for each staged prompt, captures stdout/stderr, tails files in `outputs/`, and logs synthetic trace events.

Recommendation: build the simpler first cut for workshop reliability, then upgrade to RPC streaming if time allows. The learning goal is agent anatomy and specialization, not UI engineering.

## Workshop flow: enhanced 60–75 minute version

### 0–10 min — Concept

- Commodity agent vs specialist agent.
- Agent anatomy: instructions, tools, skills, memory/files, harness, proof artifacts.
- What Reddi Agent Protocol would package/sell.

### 10–20 min — Pull and run

Participants run Docker image, open `localhost:8787`, authenticate or use fallback mode.

### 20–30 min — Generic brief

Run the generic research agent on bundled synthetic source notes.

Output: `outputs/research-brief-generic.md`.

### 30–45 min — Add specialist capability

Default path:

- agent identifies research keywords;
- calls `arxiv_search`;
- ranks papers;
- reads top PDF;
- adds evidence notes;
- improves the research brief.

Output:

- `outputs/arxiv-ranked-results.json`
- `outputs/pdf-evidence-notes.md`
- `outputs/research-brief-specialized.md`

### 45–55 min — Compare and debug

Use HTMX compare page:

- what became more specific?
- which tool calls mattered?
- did evidence quality improve?
- what should be guarded/reviewed by humans?

### 55–65 min — Package as specialist

Fill:

- `listing/marketplace-card-template.md`
- `listing/reddi-specialist-listing-template.json`

### 65–75 min — Solution + next steps

Show `solution/`, explain how it differs from starter, and invite participants to adapt it.

## Anti-stuck design

Participants should never be blocked by auth, typing errors, or slow model behavior.

Include:

- `solution/` final folder;
- `fallback/` sample outputs;
- one-click “copy solution into workspace” button;
- “reset to starter” button;
- prewritten prompts as copy buttons;
- visible health checks: Pi installed, auth detected, arXiv reachable, output folder writable;
- facilitator rule: do not debug one participant more than 5 minutes; move them to fallback/solution mode.

## Build milestones

### M1 — Public image skeleton

- Dockerfile installs Pi pinned to `0.74.0`, Python deps, Node deps.
- Copies starter, solution placeholder, fallback files.
- Starts web app on localhost port `8787`.
- `docker run` works on a clean machine.

### M2 — arXiv/PDF tools

- `tools/arxiv_search.py` smoke-tested.
- `tools/pdf_read.py` smoke-tested against arXiv PDF.
- Project-local Pi extension exposes tools.
- Agent can call tools and write ranked evidence outputs.

### M3 — HTMX UI

- Home, run, traces, compare, solution pages.
- Buttons invoke staged prompts.
- Outputs render without refreshing.

### M4 — Complete solution folder

- Final `AGENTS.md`, skills, prompts, tools, outputs, and listing JSON.
- Participant can peek or copy solution.

### M5 — Registry publish + rehearsal

- Push to public registry.
- Test from a fresh machine/account:
  - pull image;
  - run image;
  - auth path;
  - fallback path;
  - generic + specialist outputs;
  - solution peek.

## Open decisions

1. Registry target: Docker Hub org, GHCR, or other public registry?
2. Provider plan: participant personal auth, instructor-provided short-lived key, or both?
3. Session length: 60, 75, or 90 minutes?
4. Target audience: builders comfortable with Docker, or mostly no-code/low-code operators?
5. Should the HTMX UI invoke Pi via RPC in v1, or use staged `pi -p` commands first for reliability?

## Recommendation

Build this as a **public Docker-first workshop kit** with:

- one image;
- `starter/`, `solution/`, and `fallback/` included;
- no baked credentials;
- arXiv/PDF tools exposed as Pi extension tools;
- HTMX UI using staged prompt execution for v1;
- CLI still available for participants who want to see Pi directly.

This gives a proper workshop arc: build, observe, specialize, compare, package, and recover if stuck.

## Hugging Face Model Swap Add-on

After participants have a working OpenAI-backed general Pi research agent, the workshop adds a portability step: rerun the same specialist agent with an open Hugging Face model.

Recommended model:

```text
Qwen/Qwen2.5-7B-Instruct
```

Participant command shape:

```bash
cd /workshop/starter
pi -p \
  --provider huggingface \
  --model Qwen/Qwen2.5-7B-Instruct \
  "Use sources/domain-packs/artificial-intelligence.md and produce the specialist research brief. Include provider/model, domain pack, evidence labels, assumptions, and open questions. Run the harness check."
```

The teaching point is not that the open model will always beat the OpenAI baseline. The teaching point is that a well-designed agent separates:

- model provider;
- tool layer;
- domain memory/files;
- prompt/skill layer;
- harness and validation.

### Domain packs included

- Artificial Intelligence
- Blockchain Development
- Cloud Computing
- Database Development

### Harness changes for the model swap

The harness now checks for model provenance and domain-pack provenance. This is important because the quality delta must be attributable: did the result change because of the model, the domain pack, or the harness?
